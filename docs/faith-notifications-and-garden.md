# 홈 알림, 친구 마당, 예약 푸시

홈 헤더의 가장 오른쪽에 통합 알림 버튼을 둔다. 로그아웃은 내 기록 헤더에만 렌더링한다. 설정에서 AI 예시 항목을 제거하고 저장된 예시 표시 상태도 초기화한다. 기존 친구·예배당 알림 설정에 묵상 활동 알림을 추가한다.

친구 탭에는 수락된 친구 목록만으로 넓은 마당을 만든다. 각 친구의 공용 sanctuary/avatars/{uid}를 구독해 저장된 최신 3D 외형을 표시한다. 무작위 목표점을 향해 천천히 거닐고 클릭하면 현재 아바타 이름을 작은 팝업으로 표시한다. 마당 아래의 요청·친구·그룹 관리는 유지한다. 온라인 상태 표시는 아니며 접속하지 않은 친구도 보여준다. 동작 줄이기 설정에서는 이동/걷기 애니메이션을 생략한다.

## 실제 동작하는 앱 내 소식

댓글·좋아요·중보기도 참여를 저장한 뒤 publishFaithActivity가 수신자의 faithNotifications/{uid}에 트랜잭션으로 알림을 보관한다. ID는 kind:targetId:sourceId로 결정해 동일 행동을 중복 생성하지 않는다. 원본 글의 소유자, 원본 댓글의 작성자/좋아요 값/중보기도 참여 기록과 인증 UID를 데이터 규칙에서 확인한다. 자기 알림, 임의 수신자·본문, 중복 ID, 원본 없는 알림은 거절한다. 댓글 작성자 UID 재지정도 막는다. 수신자는 알림을 읽고 읽음 상태는 users/{uid}/activityNotificationReads에 비공개로 저장한다. 발신자는 본인이 보낸 개별 영수증 내용만 읽을 수 있으며 수신자의 읽음 상태는 볼 수 없다. 발신자에게 수신자 전체 알림함 조회를 허용하지 않는다.

서버 함수가 없어도 앱 안의 알림함은 동작한다. 수신자가 앱을 닫아도 레코드는 남아 재접속 시 표시된다. 이 동작은 앱 밖 운영체제 푸시와 구분한다. 서버 함수가 배포되면 같은 ID를 사용하고 별도 서버 전용 전송 기록으로 푸시 중복을 방지한다.

## 예약 푸시 — 구현됨, 운영 서버 활성화는 막힘

매일 선택한 시각과 IANA 시간대를 저장하는 설정, 기기 알림 권한·PushSubscription, Web Push VAPID 키, 서비스 워커 push/notificationclick, 매분 확인하는 Cloud Scheduler 처리 및 서버 함수가 준비되어 있다. 서버 시각 대신 작업의 scheduleTime을 사용해 지연/재시도에서도 기준 분과 일별 중복 방지를 유지한다. VAPID 비밀키·구독 암호화 키는 서버 전용 경로에 보관한다. 허용된 푸시 서비스 도메인만 받아 SSRF를 막으며 만료된 구독은 삭제한다. 계정 전환 시 같은 endpoint의 소유자를 변경하고 로그아웃 시 이 기기의 구독을 해제한다.

운영 프로젝트의 Cloud Functions API와 Cloud Scheduler API가 비활성화되어 있다. 현재 배포 계정의 서비스 활성화 시도는 HTTP 403으로 거절되며 검사한 Functions 생성/갱신·Scheduler 생성·Service Usage·서비스 계정 사용 권한도 반환되지 않았다. 따라서 **앱을 닫은 상태의 매일 정시 푸시는 아직 활성화되지 않았다.**

설정은 서버 준비 여부를 먼저 확인한다. 서버가 준비되지 않으면 예약 시간과 스위치를 비활성화하고 이유를 표시한다. 기기 알림 권한 요청은 서버 상태와 분리하며, 첫 실행 안내와 설정의 알림 권한 허용 버튼에서 바로 요청할 수 있다. 실제 푸시 구독 등록은 서버 준비 후 처리한다. 서버 예약이 검증되기 전에는 켜진 것처럼 보이거나 허용 팝업만 띄우지 않는다. 이미 켜진 예약의 해제 요청은 준비 여부와 무관하게 가능하다.

활성화하려면 프로젝트 소유자가 Cloud Functions·Cloud Scheduler 및 Firebase Functions 배포 의존 API를 활성화하고, GitHub의 FIREBASE_SERVICE_ACCOUNT 배포 계정에 Functions 배포·Scheduler 생성·서비스 계정 사용 등 필요한 권한을 설정해야 한다. 배포 계정 client_email과 거절된 API 응답은 Deploy Faith Notifications 작업의 진단 로그에서 확인할 수 있다. 요금제 변경은 수행하지 않았다.

그 뒤 Deploy Faith Notifications 워크플로를 다시 실행한다. 성공 후 mark-faith-notifications-ready 스크립트가 실제 Scheduler 작업이 ENABLED인지 확인한 뒤 서버 전용 _faithNotificationsReady를 켠다. 그때부터 설정 UI에서 매일 알림을 활성화할 수 있다. API/권한 문제가 해결되기 전에는 관련 기존 건의를 완료 처리하지 않는다.

## 검증

단위/컴포넌트 테스트는 마당 이동·이름 팝업·저장된 외형, 알림 종류 필터·읽음 처리, 예약 서버 미준비/저장 실패/권한 요청/시간 설정/해제를 확인한다. Auth/RTDB 두 브라우저 계정으로 서버 함수 없이 오프라인 수신자에 세 종류 알림 전달과 읽음·중복 방지를 확인한다. RTDB 규칙은 위조·잘못된 대상·자기 알림·다른 알림함 접근·본문 수정 및 예약/키 접근을 거절한다. Functions/Auth/DB 에뮬레이터에서는 서버 트리거와 인증된 예약 API도 검증한다. 순수 서버 로직은 한국 날짜 경계, DST, 비활성화 및 구독 URL을 검사한다. 360/768/1440px 실제 브라우저에서 헤더·친구 마당·팝업·설정의 시간 입력을 확인한다.


## 첫 실행 기기 권한

AppShell의 시작 화면과 로그인/업데이트 흐름이 끝난 뒤 NotificationPermissionIntro를 표시한다. 실제 Notification.requestPermission은 사용자가 알림 허용을 누를 때 호출한다. 이 동작은 예약 서버나 로그인 없이 가능하다. 이미 허용·차단된 브라우저와 미지원 환경에서는 자동 요청하지 않는다. 허용/나중에 선택은 기기 로컬에 기록하고, 로컬 저장이 막힌 경우 탭 저장을 시도해 반복 안내를 줄인다. 설정의 알림 권한 허용도 서버 준비 여부와 분리했다.

이 권한은 OS/브라우저 알림 표시 권한이며 알람 예약 권한이 아니다. 현재 저장소는 React PWA이며 Android/iOS 네이티브 알람 예약 모듈이 없다. 사용자가 매일 시간을 설정하면 앱이 완전히 종료된 상태에서도 울리는 알람은 웹 Notification 권한만으로 구현할 수 없다. 현재 예약 푸시의 서버/API 권한 문제는 별도의 미완료 사항으로 유지한다.
